# 08 — Modelica Emission Specification

**Status:** Baseline · **Decision:** ADR-001 · **Module:** `src/spec_forge/emit/modelica/`
**Implements:** SF-MIN-04, SF-ACC-02, PRD output layer 5 · **This module owns the hard gate.**

---

## 1. Contract

```
emit_modelica(ir: SFIR) -> ModelicaArtifact   # .mo text + element↔IR id map + compile command
```

Same three properties as the SysML emitter — deterministic, total, stable — and the same prohibition: **no LLM
call in this module.** Where behaviour cannot be templated (§5), the LLM produces a *typed IR fragment* upstream
which is then emitted deterministically. The model never writes Modelica text.

> **The generated Modelica must compile.** Binary condition, checked live on a judge-supplied spec. No amount of
> explanation substitutes for it.

Everything in this document serves that sentence.

## 2. Output structure

```modelica
within SpecForge.Generated;

model TwoTankController
  "Generated by SpecForge <version> from run <run_id>"

  // 1. imports
  // 2. inner system / medium declarations
  // 3. parameters        (from IR attributes, with units and doc strings)
  // 4. component instances (from archetype modelica bindings)
  // 5. variables and state
  // 6. initial equation
  // 7. equation          (connect statements first, then behaviour)
  // 8. algorithm         (discrete controller logic)
  // 9. annotations       (experiment, documentation, diagram layout)
end TwoTankController;
```

Emitted as a **package** when the model needs more than one class (controller + plant + record types), with
`package.mo` and `package.order`. Single-file for simple cases.

## 3. Mapping rules

| IR entity | Modelica |
|---|---|
| `Part` | Component instance of `archetype.modelica.component` |
| `Part.archetype.requires` | Hoisted into the enclosing model (e.g. `inner Modelica.Fluid.System system`) |
| `Port` | The mapped MSL connector via `archetype.modelica.port_map` |
| `Connection` | `connect(a.port, b.port);` |
| `Attribute` | `parameter <Type> <name>(unit="<unit>") = <value> "<doc>";` |
| `Attribute.value_kind = numerical_device` | Parameter **plus** a mandatory comment stating it is not physical |
| `StateMachine` | See §4 |
| `Constraint (interlock)` | `assert(...)` in `equation`, with the scoped exception encoded in the condition |
| `Requirement` | Documentation annotation only — requirements do not generate equations |
| `Assumption` | Comment on the affected declaration |

### 3.1 Units are mandatory

```modelica
parameter Real T1_High(unit="m") = 0.80
  "Tank 1 high level limit. Source: CR-004 (approved 2026-03-11). Supersedes 0.78 m (URS-001 Rev A).";
```

Every parameter carries `unit=` and a doc string naming its authority. The doc string is the traceability record
surviving into the artifact a simulation engineer actually opens — the same principle as `07_sysml_emission_spec.md` §3.4.

Prefer typed SI aliases (`Modelica.Units.SI.Length`) over `Real` where the quantity is known; `Real(unit=...)`
is the fallback when it is not.

## 4. State machines

Two strategies, selected by an IR property, not by case:

| Strategy | When | Construct |
|---|---|---|
| `algorithmic` (**default**) | Single region, discrete transitions | `Integer state` + `when` clauses in an `algorithm` section |
| `state_graph` | `regions.length > 1` (parallel split/join) | `Modelica.StateGraph` steps and transitions |

L4 requires `state_graph` because its controller has a **parallel split after evaporation and a join before
cycle reset**; a single-region encoding cannot express it. L1 uses `algorithmic`. The selection is driven by
`len(ir.state_machines[].regions)` — a structural property of the model, never a case name (SF-SCP-01).

### 4.1 Algorithmic pattern

```modelica
type ControllerState = enumeration(IDLE, FILL_T1, WAIT_AFTER_FILL, TRANSFER, WAIT_AFTER_TRANSFER,
                                   DRAIN, WAIT_AFTER_DRAIN, PAUSED, SHUTDOWN);
ControllerState state(start = ControllerState.IDLE);
ControllerState resumeState(start = ControllerState.IDLE);
Real waitRemaining(start = 0.0, unit = "s");

algorithm
  // Command precedence: SHUT > STOP > START  (DR-02 D-01)
  when edge(cmdShut) then
    state := ControllerState.SHUTDOWN;
  elsewhen edge(cmdStop) and state <> ControllerState.SHUTDOWN then
    resumeState  := state;              // D-02: store interrupted state
    waitRemaining := waitRemaining;     // D-03: freeze remaining delay
    state := ControllerState.PAUSED;
  elsewhen edge(cmdStart) and state == ControllerState.PAUSED then
    state := resumeState;               // resume, do not restart
  elsewhen edge(cmdStart) and state == ControllerState.IDLE then
    state := ControllerState.FILL_T1;
  end when;
```

Three details are emitted from IR fields rather than invented, and each one is a benchmark trap:

- **`elsewhen` ordering encodes priority.** IR `Transition.priority` determines branch order. Get it wrong and
  a simultaneous STOP+SHUT resolves the wrong way — the exact behaviour DR-02 D-01 fixed.
- **`resumeState`** exists because of `Transition` targets from `PAUSED`, giving D-02/D-04 (START while running
  is ignored; START from PAUSED resumes).
- **`waitRemaining` is frozen, not reset**, because `timers[].on_suspend == "freeze_remaining"`. The alternative
  (restarting the delay) was explicitly rejected in DR-02 D-03, and a generator that restarts it produces a
  model that compiles, runs, and disagrees with the approved design.

### 4.2 Interlocks with scoped exceptions

```modelica
// Interlock: V1 and V2 never open together (DR-02 D-08) — unconditional
assert(not (cmdV1 and cmdV2), "Interlock violation: V1 and V2 open simultaneously", AssertionLevel.error);

// Interlock: V2 and V3 not together in normal operation (DR-02 D-09),
// waived in SHUTDOWN where both are commanded open by design
assert(not (cmdV2 and cmdV3) or state == ControllerState.SHUTDOWN,
       "Interlock violation: V2 and V3 open outside SHUTDOWN", AssertionLevel.error);
```

The `or state == SHUTDOWN` clause comes from `Constraint.exceptions[].scope`. Emitting the interlock without it
makes the model assert during correct shutdown; omitting the interlock entirely fails SF-ACC-04.

## 5. Behavioural equations the library cannot supply

Topology, parameters and state logic are fully templated. Constitutive physics sometimes is not — for example
L3's flux-tube reluctance relations, or L2's ACH-to-mass-flow conversion.

Procedure, in strict order:

1. **Archetype equation template.** Most cases end here; the library carries the relation.
2. **Typed equation IR.** If no template exists, an LLM pass produces a
   `BehaviourEquation` IR entity — `{lhs, rhs, variables[], quantity, unit, provenance}` — validated for unit
   consistency and variable resolution **before** emission. The emitter then renders it deterministically.
3. **Open question.** If neither succeeds, emit an `OpenQuestion` and degrade (ADR-007). Do not guess physics.

Step 2 preserves the architecture: the model contributes *content* into a validated schema, never *syntax*. An
equation that fails the unit check never reaches the file.

## 6. The compile gate

`toolchain/omc.py`. **This is the hard gate — nothing ships past a red result.**

```bash
omc --version                                   # toolchain liveness, checked at startup
omc build/omc/check_<Model>.mos                 # loadModel(Modelica); loadFile(...); checkModel(...)
```

Generated `.mos` script:

```modelica
loadModel(Modelica);   getErrorString();
loadFile("Model.mo");  getErrorString();
checkModel(SpecForge.Generated.TwoTankController); getErrorString();
```

- Non-empty `getErrorString()` or a failed `checkModel` → **compile failure** → repair loop
  (`09_validation_and_repair_spec.md` §5).
- Warnings are captured and reported, not treated as failure.
- The **exact command** is written to `runs/<run_id>/COMPILE.md` and surfaced in the UI — because the briefing
  requires the repo to contain *"at least one generated Modelica model that compiles, together with the command
  to compile it. Judges run that command."*

### 6.1 Startup liveness check

`omc --version` runs when the service starts and before any demo run, failing loudly if the toolchain is
missing. *"A compiler that will not start is a compile failure"* — and that failure must surface at startup, not
in minute 9 of a 10-minute demo slot.

## 7. Simulation

When `checkModel` passes and the IR is well posed (`simulatable: true`):

```modelica
simulate(Model, startTime=0, stopTime=<T>, numberOfIntervals=<N>,
         tolerance=1e-6, method="dassl", outputFormat="csv");
```

`stopTime` comes from the IR's verification intent where the documents state one — L1's procedure defines a
900 s demo, L2 a 24 h trend, L4 requires running **beyond 2500 s** to demonstrate cycle reset. These are
extracted values, not constants in code.

Results → `runs/<run_id>/simulation/results.csv` → plots (`10_traceability_and_reporting_spec.md` §5) and
reference-trace comparison (`09_validation_and_repair_spec.md` §7).

## 8. Known MSL hazards

Encoded as archetype constraints and checked by `V-MOD-*` rules. Each is a real failure we expect to hit, listed
here so it is fixed once rather than rediscovered per case.

| Hazard | Rule | Mitigation |
|---|---|---|
| `Modelica.Fluid` components need `inner System` | `V-MOD-001` | Hoisted from `archetype.requires` |
| `OpenTank.nPorts` must equal connected ports | `V-MOD-002` | Computed from the connection count, never hardcoded |
| Medium must be declared and consistent across a fluid network | `V-MOD-003` | One medium per connected fluid subgraph; mismatch is an error |
| Initial conditions needed for state variables | `V-MOD-004` | `start=` from IR `level_init` etc.; missing → assumption |
| Every electrical network needs exactly one ground | `V-MOD-005` | `SA-ELEC-001` |
| Every magnetic network needs exactly one magnetic ground | `V-MOD-006` | `SA-MAG-001` — L3 requires both grounds explicitly |
| Isolating valves can leave pressure/composition undefined | `V-MOD-007` | Insert `junction.volume`; `SA-NUM-001` — L4 mandates this |
| `der()` on a discrete variable | `V-MOD-008` | Continuous/discrete partition checked in IR |
| Chattering at port-level crossings | `V-MOD-009` | Regularised loss factor with hysteresis — L4's URS specifies this treatment |

`V-MOD-007` and `V-MOD-009` are not defensive engineering on our part; L4's process requirement specification
states both as modelling constraints, and its lab notebook records that the hysteresis fix is what removed the
tiny solver steps. The library encodes what the documents already told us.
